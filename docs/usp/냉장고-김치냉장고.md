## 이 문서를 읽는 법

- **핵심 USP** = 제품 상세 지면(PDP)의 **특장점 영역(`#compGoodsFeatures`) 마케팅 헤드라인을 그대로** 옮긴 것이다.
  굵은 글씨가 삼성이 지면에 띄운 문장이고, 그 뒤가 지면의 설명문이다. **상담사가 고객에게 그대로 읽어도 되는 문장**이다.
- **뒷받침 사양** = PDP 「스펙」의 값이다. **법정 표시 7종**(제품명 · 제조자/수입자 · 제조국가 · KC 인증 필 유무 ·
  동일모델의 출시년월 · A/S 책임자와 전화번호 · 품질보증기준)과 **안전인증정보**(인증기관·인증번호)는 사양이 아니라 뺐다.
- **세트(패키지) 제품**은 사양 탭이 구성품마다 따로 있다. 이 문서의 사양은 **본체(첫 탭) 것만**이고, 구성품 전체를 함께 적었다.

### 수집·검증 방법 (다시 할 때)

| 무엇 | 어떻게 |
|---|---|
| 목록 | `GET /sec/cxhr/pf/goodsList?dispClsfNo={번호}&sortType=10&page=1&rows=500` — 냉장고 `36010000`(192종) · 김치냉장고 `36020000`(138종) |
| USP 헤드라인 | PDP HTML 을 그대로 받아 `#compGoodsFeatures` 안의 `.wrap-component` 를 순서대로 읽는다. `.title`(헤드라인) · `.desc`/`.disc`(설명) · `.sub`(윗줄). **DOM 에 이미 들어 있어 브라우저 없이 받아진다.** |
| 사양 | `GET /sec/xhr/pf/compGoodsSpecList?goodsIds={goodsId}` → `productsSpec[]` 의 `dispNm1`(묶음)·`dispNm2`(항목)·`specValue1`(값) |

**사양 API 가 PDP 와 같은 값인지 브라우저로 대조했다.** PDP 는 「스펙」 길잡이를 눌러야 `#compGoodsSpec` 이 생기는데,
그렇게 렌더한 값과 이 API 값이 **6개 모델 전수에서 정확히 일치**했다 —
`RM90H91B1W` 62행 · `RR40C79057801` 43행 · `RR40C9981APGW6` 49행 · `RZ38C9891APGW6` 43행 ·
`RQ33DB7441APW6` 69행 · `RQ34C8945APG01` 51행이고, **각각에서 법정 표시 7행을 빼면 API 행수와 같다**(55 · 36 · 42 · 36 · 62 · 44).
즉 **이 API 는 PDP 사양의 완전본이며 법정 표시만 빠진 것**이다.

- 탭은 `role="tab"` 으로 찾았다. 클래스에 `tab` 이 들었는지로 보면 냉장고의 **툴팁 버튼 `button.spec-title`** 이
  탭으로 잡혀 같은 값을 여러 번 세게 된다(`RR40C79057801` 에서 실제로 6개가 잡힌다).
- 세트 5종의 탭 구성을 눌러 확인한 결과 **본체는 언제나 첫 탭**이고 나머지는 `RA-` 로 시작하는 **도어 패널**이었다.
  `RR40C79057801` 만 냉동고·냉장고·김치플러스 **3대가 진짜 다른 제품**이다.

삼성이 **같은 기술을 같은 문장으로 파는 것**이라 갈래마다 그대로 실었다. 한 곳으로 합치면
*"이 모델에 이 문장이 붙는가"* 를 상담사가 확인할 수 없다.
