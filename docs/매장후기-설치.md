# 매장 언급 후기 대시보드 — 설치 절차

2026-08-31 사장님 요청으로 만든 것이다.
*"각종 웹사이트에 우리 경원영업팀 지점들이 언급되는 후기를 스크래핑해서 일간 주간 월간
전체 누적기록을 확인하고싶은데 … 링크도 함께수집하면 좋을것같아"*

## 왜 Apps Script 인가

*"vercel 앱은 전산PC에서 보안이슈로열리지않아 구글스크립트와같은 경로로"* (사장님).
그래서 **수집·저장·화면이 전부 구글 안에서 끝난다.** 세일즈 코파일럿 앱은 자료만 받아 간다.

```
Reviews.gs (Apps Script 웹앱 + 스프레드시트)
 ├─ 시간 트리거(하루 1회 새벽 3시) → 네이버 API → 판정 → 시트 저장
 ├─ doGet()        → HTML 대시보드   ← 전산PC 에서 이 주소를 연다
 ├─ doGet(?json=1) → JSON           ← 세일즈 코파일럿 앱이 받아 간다
 └─ doGet(?run=1)  → 지금 수집
```

## 설치 (10분)

### 1. 스프레드시트와 스크립트

1. 새 Google 스프레드시트 생성 — 이름 예: **`세일즈코파일럿 매장후기`**
2. **확장 프로그램 → Apps Script**
3. `Code.gs` 내용을 지우고 **`docs/apps-script/Reviews.gs`** 를 통째로 붙여넣기
4. 왼쪽 **파일 + → HTML** 로 파일 추가, 이름을 **`ReviewsIndex`** (확장자 없이)
   → **`docs/apps-script/ReviewsIndex.html`** 을 통째로 붙여넣기
5. 저장

### 2. 네이버 키 넣기 — **코드에 적지 말 것**

**프로젝트 설정(⚙) → 스크립트 속성 → 속성 추가**

| 속성 | 값 |
|---|---|
| `NAVER_CLIENT_ID` | NAVER API HUB 의 Client ID |
| `NAVER_CLIENT_SECRET` | 같은 곳의 Client Secret |

키는 **`console.ncloud.com/naver-api-hub`** 에서 발급한다(옛 `developers.naver.com` 이 아니다 —
2026-06-25 에 이관됐고 그쪽 「사용 API」 목록에서 검색이 통째로 사라졌다).
「사용 API」에서 **NAVER 검색 → 블로그 · 카페**를 고른다. 하루 25,000 회 한도이고 우리는 88 회 쓴다.

> **이 저장소는 public repo 다.** 키를 `Reviews.gs` 안에 적으면 그대로 공개된다.
> 스크립트 속성은 그 스프레드시트를 가진 사람만 본다.

### 3. 자동 수집 걸기

함수 목록에서 **`setupTrigger`** 를 골라 **실행** — 하루 1회 새벽 3시 트리거가 걸린다.
한 번만 하면 되고, 다시 실행해도 중복되지 않는다(스스로 옛 트리거를 지운다).

### 4. 배포

**배포 → 새 배포 → 유형: 웹 앱**

| | |
|---|---|
| 실행 | **나** |
| 액세스 권한 | **전체** |

발급된 **`/exec` 주소**를 전산PC 즐겨찾기에 둔다.

### 5. 첫 수집

주소를 열고 **「지금 수집」** 을 누른다. 44개 매장 × 2소스라 **1~2분** 걸린다.

## 무엇을 어떻게 세는가 — **화면이 밝히는 것과 같다**

### 대상은 **44곳**이다 (전체 65곳이 아니다)

캠퍼스·사업장 안 **모바일 전용점 21곳을 뺐다.** 실측(2026-08-31)으로 그 21곳은
블로그·카페 **전부 0건**이다 — 공개 후기가 구조적으로 없다. 매일 두드려도 0 이라
호출만 낭비고, 대시보드에 「0건」이 21줄 늘어서면 진짜 신호가 묻힌다.

### 일간·주간·월간은 **「발견일」** 기준이다

**카페 검색 결과에는 작성일이 아예 없다**(블로그만 `postdate` 를 준다). 그래서 우리가
**처음 본 날**로 센다 — 매일 돌며 새로 잡힌 것만 더하므로 *"그날 새로 발견된 후기"* 라는
정직한 뜻이 된다. 블로그는 작성일도 함께 담아 화면이 둘을 갈라 적는다.
**작성일인 척하지 않는다.**

### 중복은 **링크 URL** 로 막는다

같은 글이 매일 검색에 잡히므로 이것이 없으면 누적이 매일 부풀어 오른다.

### URL 은 건수와 **이어져 있다**

2026-08-31 사장님 지시 — *"해당 바이럴건수에 url도 함께수집이되어야합니다"*.
수집은 처음부터 `link` 열에 담고 있었지만 **화면이 200 건만 받아** 매장별로 골라 볼
수가 없었다. 건수만 있고 링크로 갈 길이 없으면 *"북수원 50건"* 을 보고도 그 50 개를
확인할 수 없다. 셋을 고쳤다:

- **매장·카페 막대를 누르면 그 링크만** 보인다(다시 누르면 풀린다).
- 화면이 **무엇으로 걸렀는지와 몇 건인지** 함께 적는다(`매장 북수원 ✕  50건`).
- **CSV 로 내려받는다** — 지금 걸린 거름망 그대로 담기므로 그 매장 링크만 받을 수 있다.
  파일명에 매장 이름이 들어간다(`매장후기_북수원_2026-08-31.csv`).

**목록·CSV·건수가 같은 함수(`filtered()`)를 본다** — 따로 세면 화면이 「50건」이라
적고 CSV 에는 48건이 담기는 어긋남이 난다.
**CSV 에 BOM 을 붙인다** — 없으면 엑셀이 UTF-8 을 못 알아보고 한글이 통째로 깨진다.

## 판정 — **이 기능의 성패가 여기 걸려 있다**

네이버 검색은 **따옴표를 강제하지 않는다**(따옴표 유무로 결과가 같았다). 그래서 API 가
주는 `total` 을 그대로 믿으면 안 된다. 실측:

| 검색 | API `total` | 진짜 |
|---|---|---|
| `삼성스토어 수원` | **340** | **3건** — 나머지는 청담점·AK수원·북수원·**축구단 굿즈샵** |
| `삼성스토어 광주` | **944** | **0건** — 전부 광주광역시(우리는 경기 광주) |
| `삼성스토어 기흥삼성SDI` | 145 | **0건** — 전부 주식 블로그 |

**0건보다 나쁜 것이 「조용히 틀린 답」이다.** 대시보드에 「수원 340건」이 뜨는데 실제로는
3건이면, 화면만 봐서는 영영 모른다.

### 규칙 넷 (전부 실측에서 나왔다)

1. **브랜드 + 매장명이 붙어 나와야 한다** — 앞뒤 어느 쪽이든. 띄어쓰기는 무시한다
   (`삼성 스토어` 로 띄어 쓴 글이 있다). 옛 이름 `삼성프라자`·`디지털프라자` 도 받는다.
2. **더 긴 이름이 걸리면 그쪽 것이다** — `수원` 30건 중 9건이 `AK수원`·`북수원`·
   `스타필드수원`·`타임빌라스수원` 이었다.
3. **꼬리표가 근처에 있으면 그 체인점 것이다** — `삼성 스토어 평택 ak점` 은 붙여 쓰지
   않아 2번에 안 걸린다. **단 자기 이름에 이미 꼬리표가 있으면 이 규칙을 걸지 않는다** —
   안 그러면 `AK분당` 이 자기 후기를 남에게 넘겨 60건이 2건이 된다(실제로 한 번 그렇게
   무너뜨렸다. **막는 쪽만 보고 고치면 이 반대쪽 실패가 난다**).
4. **축구단을 걸러낸다** — `수원삼성` 은 프로축구단이고 `블루윙즈스토어` 라는 굿즈샵이 있다.
   검색해 보기 전엔 있는 줄도 몰랐던 함정이다.

### 「광주」는 **검색어를 바꿔서** 풀었다

배제어로는 못 푼다 — 실측 16건이 전부 광주광역시였고 그중 절반은 본문 어디에도
광주광역시 표시가 없다. `삼성스토어 경기광주` 로 물으니 **9건이 전부 진짜**다.
**글쓴이들이 스스로 「경기광주」라고 적는다** — 자기도 헷갈릴 걸 알기 때문이다.

> **규칙을 정교하게 만드는 것보다 질의를 고치는 쪽이 원인에 가까웠다.**
> 이름이 전국에 겹치는 매장이 더 나오면 `QUERY`·`MATCH` 에 한 줄씩 더한다.

### 실측 정밀도 (2026-08-31, 44개 매장 전수)

```
받음 2,341건 → 통과 1,465건 (62.6%)
  블로그 706 · 카페 778
  0건 매장 0곳
```

표본을 손으로 전수 확인했다 — 통과분은 진짜 후기였고(매니저 이름까지 나온다),
탈락분은 전부 다른 매장·다른 지역·축구단이었다.

## 네 소스가 두 엔드포인트로 다 덮인다

| 소스 | 어디서 받나 | robots |
|---|---|---|
| 네이버 블로그 | 공식 검색 API | 해당 없음(API) |
| 네이버 맘카페 | 공식 검색 API | 해당 없음(API) |
| **다이렉트웨딩** | 같은 API (`cafe.naver.com/directwedding`) | 자체 사이트는 `ClaudeBot` 명시 허용 |
| **메이크마이웨딩** | 같은 API (`cafe.naver.com/makemywedding`) | 자체 사이트는 **서버가 403** |

**자체 사이트는 긁지 않는다.** 정작 후기가 카페에 쌓이고(메이크마이웨딩 공식 안내가
스스로 그렇게 적는다 — *"카페에 상담 후기 남겨주신 전원 신세계 상품권"*), 사이트마다
스크래퍼를 만들면 구조가 바뀔 때마다 **조용히 0건**이 된다.

**`cafe.naver.com` 자체는 `Disallow: /` 에 RAG 금지까지 명시**돼 있어 직접 긁으면 안 된다.
공식 검색 API 로 받는 것은 네이버가 스스로 내주는 자료라 그와 다른 일이다.

## 고치는 자리

| 무엇 | 어디 |
|---|---|
| 수집·판정·집계·화면 | `docs/apps-script/Reviews.gs` |
| 대시보드 화면 | `docs/apps-script/ReviewsIndex.html` |
| 대상 매장 | `Reviews.gs` 의 `STORES` (44곳) |
| 검색어 예외 | `Reviews.gs` 의 `QUERY`·`MATCH` |
| 잡음 배제어 | `Reviews.gs` 의 `NOISE` |

**`Reviews.gs` 를 고쳤으면 반드시 다시 배포할 것**(배포 관리 → 새 버전).
저장만으로는 안 바뀐다 — 게시판·로그와 같다.

### 판정을 고쳤으면 대조할 것

`.gs` 는 순수 자바스크립트라 판정 함수를 떼어 와 실제로 돌려 볼 수 있다.
`.scratch/_gscheck.mjs` 가 그 일을 한다 — **옮겨 적다 어긋나면 배포 후에야 숫자가
다른 것을 알게 된다.**
